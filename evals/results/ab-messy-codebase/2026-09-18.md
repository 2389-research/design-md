# A/B — messy codebase — 2026-09-18

Follow-up to the 2026-07-24 lifecycle A/B, which found a near-tie on pixels and
flagged its own caveat: "the single-shot delta was modest *because the test site
is already disciplined*… Follow-up eval candidate: same A/B on a project with no
existing visual system." This is that eval.

## Setup

**Fixture.** Built blind — a separate Claude Code session with no plugin and no
knowledge of this hypothesis, prompted only: "build me a small personal site -
landing page, about page, and a projects page. plain html and css, no
frameworks, no build step. don't worry about polish, i just want something up
quickly."

*Finding before the eval even started:* that prompt did **not** produce a messy
codebase. Opus 5 wrote `:root` custom properties on the first pass. You cannot
get drift by asking for it. Drift was produced the way it actually happens — by
accretion, via three further one-off feature asks (a "now" box, project tags,
a contact page with a CTA), each blind.

Resulting fixture state (frozen at `bca3b78`, both arms byte-identical):

- 4 tokens in `:root`, but **9 hardcoded color usages outside it** — including
  an undeclared accent-dark `#2f49af` used 3×, two near-whites, a one-off border
  grey `#c9c9c9`, and two tinted panels `#f1f3fb` / `#f5f5f4`
- **23 distinct rem values**, no spacing scale
- `.tag` / `.tags` / `.button` vocabulary existing but documented nowhere

**Arms.** Both driven live in tmux, `--dangerously-skip-permissions`, isolated
`XDG_STATE_HOME`.

- **Control:** vanilla Claude Code, no plugin, no DESIGN.md.
- **Treatment:** plugin loaded; DESIGN.md created first via the `design-md`
  skill in extraction mode (364 lines, validator `OK`), committed, then the
  build prompt.
- **Build prompt, byte-identical, zero design instructions:** "add a writing
  section - an index page listing posts, and a page for an individual post."

## Result

| | Control | Treatment |
|---|---|---|
| Diff | +84 / −0 | +94 / −6 |
| New hardcoded hex | **1** (`#f5f5f4`) | **0** |
| New `:root` tokens | 0 | 1 (`--mono`) |
| Shared-rule handling | duplicated (`.post-list` "mirrors `.project-list`") | unified (`.project-list, .post-list`) |
| Conflicts surfaced | none | 1, refused to self-resolve |
| Pre-existing bugs found | 0 | 1 (verified real) |
| Cost / wall-clock | $1.01 / 2 min | $3.56 / 11 min (incl. DESIGN.md creation) |

### Where the treatment measurably won

1. **The decisive case — same element, different outcome.** Both arms styled
   `.post pre`. The control gave it `background: #f5f5f4` — the *tag-pill tint*,
   reused for an unrelated purpose, no token declared. The treatment gave it no
   background at all: border on paper. DESIGN.md's recorded rule ("tag pills and
   the Now box are the only tinted surfaces, everything else stays on paper")
   is exactly what prevented it. This is drift propagation caught in the act,
   and it is the clearest single result either A/B has produced.
2. **Surfaced a genuine conflict instead of quietly resolving it.** Code needs
   fixed-width type; DESIGN.md says "Don't add a second typeface." The treatment
   added `--mono` scoped to code, then stopped and said it would not amend a
   don't the user had set, offering two resolutions. The control never hit the
   question — it added no `font-family` at all and silently inherited the
   browser's default monospace.
3. **Found a real latent bug.** `.tags { margin: 0.5rem 0 0 }` is overridden by
   the more specific `.project-list p { margin: 0 }`, so the 8px gap above
   project tags has never rendered. Verified independently. It declined to fix
   it (pre-existing, changes the projects page) and handed the call back.

### Where the treatment lost, or the result is not clean

1. **Extraction fidelity failure.** DESIGN.md contains an `error: #b3261e` token
   that appears **nowhere** in `style.css` — invented during extraction, in a
   file whose entire brief was transcription. The treatment self-reported this,
   which is the right behavior, but the invention should not have happened.
   Verified: 2 occurrences in DESIGN.md, 0 in source.
2. **Blast radius inverted vs. the last A/B.** There, the treatment was purely
   additive and the control refactored a shared component. Here it is the
   reverse: the control was +84/−0, the treatment edited existing
   `.project-list` selectors to share them with `.post-list`. The treatment's
   version is better structured and it named the shared concept, but "treatment
   is more conservative" is **not** a durable finding — it did not replicate.
3. **Cost.** ~3.5× the dollars and ~5× the wall-clock, including DESIGN.md
   creation. The build turn alone was roughly 2×.

## Caveat on method

The treatment's seeding questions were answered by the operator, choosing
"variant 1 — today's site" so DESIGN.md would be a *record* rather than a
redesign, keeping the arms visually comparable. That means the treatment
received a human-in-the-loop step the control never got. **This eval measures
the value of having a written design system, not the value of the interview that
produces one.** A stricter design would give the control an equivalent
human-attention step.

## Two further arms

The two-arm result above changed only one variable in aggregate (file *and*
plugin), so it could not say which half did the work. Two more arms, same
frozen fixture `bca3b78`, same build prompt, ran to settle it.

**Arm 3 — "just tell it to be consistent."** Vanilla Claude, no DESIGN.md,
build prompt plus one sentence: "keep it consistent with the existing styles."
Hypothesis: a free sentence makes the plugin redundant. **It did the
opposite.** It invented *two* near-white tints present nowhere in the fixture
(`#f7f7f5` on `pre`, `#f0f0ee` on `code`) — worse than saying nothing, since
the plain control at least reached for a color already in the file.
"Consistent" has no referent when the codebase itself is inconsistent; a vague
instruction licenses plausible invention, a token list does not.

**Arm 4 — DESIGN.md, no plugin.** The treatment's created DESIGN.md committed
into the fixture, vanilla Claude, no plugin loaded. It matched the full plugin
exactly, and reproduced the reasoning, not just the output:

- Found and read DESIGN.md unprompted, off a plain directory listing. No
  pointer hook involved.
- Surfaced its judgment calls without being asked — "Two judgment calls worth
  naming."
- Hit the same monospace-vs-"don't add a second typeface" conflict the
  treatment hit, and resolved it *more* strictly: it deleted an inline `<code>`
  element because an unstyled `<code>` "smuggles the second typeface back in
  through the default stylesheet." The treatment declared a `--mono` token and
  asked permission.

### Final scoreboard — off-token colors introduced

| Arm | DESIGN.md | Plugin | New hardcoded hex | Tinted `<pre>`? |
|---|---|---|---|---|
| Control | no | no | 1 (`#f5f5f4`) | tinted |
| "Be consistent" | no | no | **2** (both invented) | tinted |
| DESIGN.md only | **yes** | no | **0** | clean |
| Full plugin | yes | yes | **0** | clean |

## Verdict

**The artifact does the work. The enforcement layer does not.**

On a messy codebase, having a written design system is worth real money —
zero off-token colors versus one or two without it, and the caught case is
concrete rather than argued. On a disciplined codebase it is a near-tie
(2026-07-24), which is consistent rather than contradictory: there, imitation
already suffices.

But DESIGN.md alone reproduced the full stack's result *and* its reasoning,
while the enforcement stack cost ~3.5× and, in the one place it differed,
performed slightly worse. Acting on this, `using-design`, the pointer hook,
and the Stop audit hook were removed. The creation skill, template, validator,
and the one-time creation-offer hook remain.

Also retired by this eval: the "treatment is more conservative about blast
radius" claim from 2026-07-24 — it inverted here and does not replicate.

## What this eval does NOT establish

The enforcement layer was removed on a single-turn task in a six-file repo
with DESIGN.md at the root. Two cases could still favor it and remain
untested:

1. **Deep repository.** Discovery succeeded here because a directory listing
   surfaced DESIGN.md immediately. In a large tree an agent may never see it.
2. **Long session.** The file could fall out of context over many turns; the
   Stop hook re-injected the obligation every turn.

If either is later shown to matter, the removed code is recoverable from
history — this record is the argument it would have to beat.

## Method notes and confounds

- The treatment's seeding interview was answered by the operator, choosing
  "variant 1 — today's site" so DESIGN.md recorded rather than redesigned.
  That is a human-in-the-loop step arms 1-3 never received. Arm 4 removes
  this confound for the enforcement question (it received the *finished*
  file, no interview), but not for the creation question.
- Arms 3 and 4 needed a follow-up prompt ("posts will sometimes include code
  samples") to reach the code-block decision, which arms 1 and 2 reached
  unprompted. The decisive comparison is therefore on the same *situation*,
  not the same prompt count.
- Extraction fidelity failure stands: DESIGN.md contained `error: #b3261e`,
  a token in no stylesheet, invented during transcription and self-reported.
  Fixed afterward by the token-provenance rule in the skill's Phase 4.
